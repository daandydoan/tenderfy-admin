Brief · Super-admin onboarding

Set up once, bid forever

Tenderfy staff set up each client's tender kit once — brand, blocks, documents, tender template. The client's estimators only ever fill in the words.

Prototype at daandydoan.github.io/tenderfy-admin · Daniel · 16 Sep 2026 · page 1 for Tom, Shivam, sales · page 2 for devs

Why an admin builds it, not the client

A client sends us a logo, a brand guide and their last few tenders. They don't know what a block is and shouldn't need to. An admin (Ray suggesting) turns that evidence into a kit; the client only has to say yes to the brand. Two things this buys: time to first tender — the client's first bid is a fill-in, not a build — and consistency — every tender they send renders from one approved brand through one renderer.

Cost: roughly N hours of admin time per client, by whoever owns onboarding, once. The client hands over: logo, brand guide (or an old tender that shows it), and the tender sections they reuse. Lead time to a fillable template: N days.

In plain terms: a block is one section (a safety statement, a resume, a case study). A document is one or more pages made of blocks. A tender template is the whole bid — documents in a fixed order. Brand sits across all of it and is painted on at output.

The pipeline

  1. BrandDerive → client approves
  2. BlocksSections, per client
  3. DocumentsPages from blocks
  4. Tender templateDocuments in order, assigned
  5. Client editorEstimator fills · out of scope
  6. PDF at IssueBrand frozen here

One renderer draws the block canvas, the document preview and the final PDF from the same data. A sent tender pins the brand version it was issued with; later brand edits affect drafts only.

Decided · Blocking · Deferred

Decided no re-opening

  • Blocks belong to a client. No permission controls in the admin builders.
  • Brand is applied by the renderer, one renderer everywhere (canvas = preview = PDF).
  • One shared component library across super-admin and business-admin (5 Aug).
  • Autofill removed; manual editing. No stepper. Resume builder deferred.
  • A4 standard; PDF is generated by the backend and downloaded from the client side.

Blocking needs a call before scoping

  • Styling ownership. Proposal: brand owns type and colour; block owns layout and emphasis. Today the prototype allows element-level typography overrides inside a document and hides fill/stroke/layout overrides. If the proposal stands, typography overrides go too.

Deferred to the client editor

  • Fixed / Editable / Locked permissions, "add another item" on repeat rows, audit trail, lock-by-head-office, document versioning. Out of scope here — but this is where most of the hard state lives, so it is most of the remaining cost.

Not in this build

  • AI Draft from a client file is a keyword match on the description today. The real build reads the image. not built
  • The client editor and the backend PDF renderer. The admin side ends at "assigned".
  • Rebrand path: a brand change creates a new approved version; issued tenders keep theirs. Not modelled beyond the freeze rule.
  • Pagination never splits a block taller than a page.

Page 2 · for developers

What the prototype models

Static HTML/JS, persistence in localStorage. Shared code: block-layouts.js (elStyle, composeBlock, blockDocCopy), document-render.js (pagination), editor-shared.js, components.css. Full notes in DEMO-NOTES.md.

Brand (per client)

brand.evidence[key]   {from, page} | {assumed:true} | {derived:true}   key = colour role or font
brand.approval        {status: not-sent | pending | approved, by, date}
brand.log[]           {date, by, what}
document.issued       {date, brandSnapshot}                           frozen at issue

Block

{ id, name, category, client, generic?,
  doc: [ { cols:[[el]], ratio?, valign?, repeat?:'v'|'h' } ] }      rows → columns → elements
el = { id, st, content }                                             st = per-element layout/typography/appearance

Document

{ id, name, category, status, desc, type:'section'|'page', client,
  docStyle:{bg, pad, gap, rad}, topLayer:{header, footer}, docBg:{mode:'regions', regions:[]},
  blocks:[ { t:'block'|'element', id, style, content?, doc? } ] }
blocks[i].doc = this document's copy of the block; exists only once edited; "Revert" deletes it

Invariants

  • Saving a document never writes to a block. Editing a block never rewrites documents.
  • Rendering = elStyle(st, brand). Same function for canvas, preview, PDF. No second renderer.
  • No document is built on a brand that isn't approved. An issued document renders from its snapshot.
  • Repeat rows are block structure; instances ("add another") are a client-editor concern.

Needed for v1 that the prototype doesn't decide

  • Server IDs and versioning for brand (the snapshot a tender pins), blocks and documents; per-user drafts.
  • Where the PDF renderer runs (backend) and how it shares elStyle with the front end — the 5 Aug shared-library decision constrains this to one component library.
  • AI Draft: store the source image and what was read from it (provenance).
  • Pagination that splits long blocks/tables across pages.

What the prototype fakes (look for the concept badge)

  • AI Draft / Suggest blocks: keyword match, file ignored.
  • "Used in N" counts are seeded.
  • Repeat rows render twice as a stand-in for "one per item".
  • Assign / QA / Issue are toasts, no workflow behind them.
